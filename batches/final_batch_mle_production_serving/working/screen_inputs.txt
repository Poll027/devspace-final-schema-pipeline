
mle.prediction_schema_validation
tb1 intro An endpoint receives JSON, but a parseable body can still violate the prediction contract. Decode first, then validate fields, types, boundaries and the response alignment before accepting it as a successful prediction request.
tb2 definition A prediction request schema declares the expected features, their types and permitted values, and a response schema declares the expected output structure. Decode the incoming JSON into Python values before validating field presence and value types; raw JSON text is not the structured request. Compare required and supplied key sets, then check each value’s declared type or numeric boundary with conditional predicates.
tb3 mechanism For matrix-valued inputs, construct the declared NumPy representation and verify rank, feature width and output row alignment against the request/response contract. Reject malformed or out-of-contract requests explicitly rather than returning a successful prediction from invalid inputs. Write assert predicate checks for the declared valid, boundary and failure cases; a false predicate raises AssertionError during ordinary non-optimized execution.
tb4 mechanism Send a JSON request body as encoded bytes in urllib.request.Request(url, data=body, headers={"Content-Type": "application/json"}, method="POST"), then read the response through urlopen with a stated timeout. Use json.dumps to encode structured request/response values and json.loads to decode JSON before checking their fields.
tb5 example Suppose the request contract permits a two-feature matrix with one row per order. A body decoding to three rows of two permitted values can be checked for rank and width, then the response must have the declared row alignment. A body missing a required key fails before prediction. A numeric boundary fixture can test an included limit and a value just beyond it. Send the serialized body as encoded bytes with the declared JSON header and a bounded timeout, decode the returned JSON and inspect its fields. Parsing success, request validity and response correctness are three different checks; retain each failure explicitly rather than returning a successful result for malformed input.

The schema checks must happen before using a field as model input. Check that the required key exists, that its value has the declared type and that its dimensions and values satisfy the stated predicates. A missing key and an out-of-range value are different rejected fixtures. After prediction, inspect the structured response independently: required output keys, row correspondence and declared value or shape expectations. Bounded request timing is part of the fixture transport, not a substitute for contract validation. Explicit rejection distinguishes invalid input from a successful prediction containing the wrong data.
tb6 misconception Raw JSON text is not the structured request, and successful JSON decoding is not schema acceptance. A response with the wrong row correspondence still violates the prediction contract.

mle.bounded_batch_inference
tb1 intro The supplied dataset needs predictions in bounded chunks. The output must preserve observation identity even if serialization or later inspection changes row order. Reuse the fitted state for every chunk.
tb2 mechanism Use the format-appropriate bounded reader, such as pd.read_csv(path, chunksize=declared_rows), to iterate the input dataset rather than requiring it all in memory. Apply the fitted preprocessing/model to each chunk without fitting new state during inference. Preserve each chunk’s observation keys alongside predictions and verify one result per eligible input key, rather than relying on a changed output row order.
tb3 mechanism Write output records in the declared serialized format and decode the written fixture again to verify its schema and observation alignment. Write assert predicate checks for the declared valid, boundary and failure cases; a false predicate raises AssertionError during ordinary non-optimized execution. Use explicit with open(...) handles for input/identity or output records, and write one bounded set of prediction records before reading the next batch.
tb4 example Suppose five keyed orders are processed in chunks of two, two and one. Apply the fitted preprocessing and model to each chunk, keeping each order key with its prediction. Write that bounded set of serialized results before reading the next chunk. Decode the written fixture again and verify its schema and one-result-per-eligible-key correspondence. A missing key or duplicate output is a failure even if the total number of rows looks reasonable. Keep explicit input and output handles and the declared reader format. The procedure is inference over chunks, not fitting a new model or preprocessor for whichever chunk happens to arrive next.

Keep an output key beside its prediction through serialization, not merely in a temporary input structure. After writing, decode the fixture and compare key coverage against the eligible input IDs. A duplicate result for A plus a missing result for B could leave the total row count unchanged, which is why correspondence needs more than counting rows. Each chunk uses the same fitted objects and declared response schema. The bounded writer and reader handles establish where results were produced and re-inspected. This completes an inference path whose correctness includes persistence and identity, not only in-memory prediction values.
tb5 misconception A matching total row count does not guarantee one result for every eligible input key. Batch inference preserves keys and fitted state, rather than relying on incidental output order.
