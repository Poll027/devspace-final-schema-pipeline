mle.tile.064_065.s02 Resolve configuration before deployment
Use docker compose -f CONFIG_PATH config to parse, resolve and validate the authored YAML before applying it; check its resolved fields against the intended runtime contract.
Apply the declared local Compose deployment with docker compose -f CONFIG_PATH up -d and inspect the resulting containers.
Set replica count at services.<service>.deploy.replicas; set resource bounds at services.<service>.deploy.resources.limits.cpus and memory in a runtime supporting these deploy fields, and validate the resolved count and bounds before applying the configuration.
Keep secrets out of Dockerfile ARG and ENV: they persist in the final image or its metadata.
Deliver sensitive values through runtime secrets, never as literal Compose values.
After application, inspect the running image identity and compare it with the recorded artifact reference.

Connect to the running authorized VM with gcloud compute ssh INSTANCE --zone=ZONE to execute the workload.
Use gcloud compute instances describe INSTANCE --zone=ZONE to inspect the instance status and identity before and after the authorized lifecycle action.
Create the configuration branch with git checkout -b BRANCH, commit the verified configuration, then merge the branch under the existing repository workflow.
Destroy only the test deployment with docker compose -f CONFIG_PATH down, then reapply the same file and verify identical image identity and resolved runtime settings.

mle.tile.064_065.s04 Verify immutable deployment configuration
In the fixture, configure the approved immutable image, declared port mapping, supported replica count and resource bounds. Safely reload the YAML and inspect compose config before applying it. Compare the running image with the recorded artifact, then commit the verified configuration through the existing branch and merge workflow. Destroy only the test deployment, reapply the same file and verify identical identity and settings. Use only authorized VM lifecycle and connection actions. Secret references name injected variables, never credential values.
A mutable tag is not the immutable release identity. Parsed configuration also does not prove running state, and deploy resource fields must be supported by the supplied runtime.

mle.tile.064_065.s07 Verify a model release on an existing runtime
A launch message is not release acceptance. Verify identity, execution state and bounded endpoint behavior.
Verify the same recorded artifact and runtime configuration in the existing execution environment, rather than accepting the fact that deployment started as proof of a correct release.

Inspect the running container identity and State, including Health when a healthcheck is configured, and compare them with the intended release.
Inspect runtime logs for initialization and execution failures without copying sensitive request data or credentials into the evidence record.

mle.tile.064_065.s08 Probe readiness and prediction contracts
Call the declared readiness and prediction endpoints with bounded timeouts and check the returned status and payload against the expected contracts.
Send a JSON request body as encoded bytes in urllib.request.Request(url, data=body, headers={"Content-Type": "application/json"}, method="POST"), then read the response through urlopen with a stated timeout.
Serialize structured request/response values with json.dumps; decode JSON with json.loads before inspecting fields.
Inspect the small prediction fixture’s output shape and values against the declared task/response contract.
Assert the declared valid, boundary and failure predicates. In ordinary non-optimized execution, a false assertion raises AssertionError.

mle.tile.064_065.s09 Compare the running release with its record
Inspect the named fixture container against the release record: image, State and Health when configured. Review initialization and execution logs without copying sensitive requests or credentials. Call readiness and prediction with stated timeouts, sending encoded JSON and decoding the response. Verify status, output shape and declared values with assertions. Plausible predictions do not repair an image-identity mismatch; retain separate identity, initialization and contract checks.
Launch success is not release verification. A correct-looking prediction is insufficient if the artifact identity or runtime configuration differs from the intended release.
