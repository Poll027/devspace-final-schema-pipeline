mle.training_fitted_imputation
tb1 An order feature is missing in some rows. A replacement learned from training is part of the fitted representation; it should not change just because validation contains a different mix of values. Separate learning the replacement from applying it.
tb2 SimpleImputer learns one replacement value per feature from the data passed to fit, with strategies including mean, median, most_frequent and constant. Use SimpleImputer(strategy=declared_strategy).fit(X_train), then call transform(X_validation) without fitting on validation rows. Inspect statistics_ to check the fitted replacement values and verify they remain unchanged after validation transformation.
tb3 Compute the arithmetic mean with np.mean(numeric_values, axis=0), so each selected numeric feature column is summarized over rows. Compute standard deviation with np.std(numeric_values, axis=0, ddof=0), which divides squared deviations by N before taking the square root; use ddof=1 only when the stated calculation requires the N−1 divisor. Write assert predicate checks for the declared valid, boundary and failure cases; a false predicate raises AssertionError during ordinary non-optimized execution.
tb4 Suppose the observed training distances are 2 and 6, and the declared strategy is mean. Their mean is 4, so the fitted replacement for a missing distance is 4. If validation contains distance 100 and a missing value, transform it using the stored replacement rather than incorporating 100 into a new mean. Inspect statistics_ before and after transformation to confirm the replacement stayed fixed. Keep checks for a complete row, a missing row and the declared boundary case. If the readiness calculation also asks for feature spread, use the specified standard-deviation divisor on the selected numerical observations; that summary is distinct from selecting the imputer strategy. Other supplied strategies may call for a different replacement, so do not treat this example's mean as a general requirement.

The missing validation row is an application case for the stored statistic. It is not an extra observation from which to relearn the statistic, and the observed value 100 belongs to the held-out cohort rather than the training reference. Check the transformed result and statistics_ together: the expected replacement verifies the output, while unchanged statistics verify reuse of the fitted state. This distinction remains important if the supplied strategy is median, most_frequent or constant instead of mean. The chosen strategy defines how the replacement is learned or supplied; the train-versus-transform boundary defines when its state may change. Preserve both choices in the bounded workflow.
tb5 Calling fit on validation learns a different state. Transforming validation is reuse of the training state, not a request to choose a replacement that looks more suitable for the held-out rows.
mle.training_fitted_scaling
tb1 Training and validation orders have different distance ranges. Scaling should put both through the same fitted rule, not make each cohort define its own reference. The training mean and scale are the state you inspect and reuse.
tb2 StandardScaler centers each feature using its training mean and scales by its training standard deviation when with_mean and with_std are enabled. Fit StandardScaler on X_train and reuse its transform on X_validation; mean_ and scale_ expose the stored training parameters. A constant feature cannot be scaled to unit variance, so StandardScaler leaves its scaling factor as 1.
tb3 Validation and prediction inputs must receive the transformations used for training, rather than separately fitted transformations. Compute the arithmetic mean with np.mean(numeric_values, axis=0), so each selected numeric feature column is summarized over rows. Compute standard deviation with np.std(numeric_values, axis=0, ddof=0), which divides squared deviations by N before taking the square root; use ddof=1 only when the stated calculation requires the N−1 divisor.
tb4 Write assert predicate checks for the declared valid, boundary and failure cases; a false predicate raises AssertionError during ordinary non-optimized execution.
tb5 Take a training feature with values 2 and 6. Its mean is 4 and its population standard deviation is 2. With centering and scaling enabled, those values become −1 and 1. A validation value of 8 becomes (8−4)/2 = 2 under the stored training rule. Separately fitting validation would no longer apply that rule. Inspect mean_ and scale_ and check that validation transformation does not replace them. Include a constant-feature fixture: the scaler uses a scaling factor of 1 rather than turning a constant feature into unit variance. Record feature-wise summaries over rows with the specified divisor so the reference calculation and the fitted parameter interpretation remain aligned.

A validation value beyond the training range can legitimately receive a transformed value beyond the training fixture's transformed values. The value 2 for validation distance 8 follows the fixed formula; it is not a reason to refit until validation has its own mean zero. Verify the column-wise mean and population spread used in the hand calculation, then inspect the fitted parameters corresponding to that feature. Centering and scaling configuration also matters: the stated formula assumes both are enabled. For a constant training feature, report the factor of 1 and the resulting behavior rather than describing an impossible unit-variance transformation. All later cohorts reuse this same fitted interpretation.
tb6 Scaling is not ‘make every incoming dataset have its own zero mean.’ Validation and prediction reuse training transformations; a constant feature cannot be forced to unit variance by that scaler.
mle.categorical_encoding
tb1 An order's zone is a category rather than a numerical distance. The fitted category mapping determines the indicator columns. Before accepting held-out rows, make explicit what happens to a category the training fit never encountered.
tb2 OneHotEncoder learns categories from fit data and represents each categorical value with the corresponding indicator columns. Fit the encoder on the training categories, inspect categories_, and use transform for validation inputs without relearning the mapping. Choose handle_unknown explicitly: its default error rejects unknown categories, whereas ignore produces all-zero indicators for an unknown category in that feature.
tb3 Missing categorical values can be represented as a learned category when present at fit time; missing values absent from the learned categories follow the unknown-category behavior. Write assert predicate checks for the declared valid, boundary and failure cases; a false predicate raises AssertionError during ordinary non-optimized execution. Build the training-category dictionary from the fitted encoder’s categories_ and feature names, and keep list-based known, unseen and missing cases aligned with that stored mapping.
tb4 Suppose training contains north and south. Inspect categories_ and store the category dictionary with the feature name, using the fitted order rather than inventing a new one. Under a two-column north/south mapping, a known north row has its corresponding indicator set. An unseen east row is rejected by the default error policy; with handle_unknown set to ignore, it has all-zero indicators for that feature. Keep known, unseen and missing fixtures aligned with the stored mapping. Missing values present during fit can become a learned category; missing values absent from the learned set follow the unknown-category behavior. That distinction means two missing-value fixtures may need different expectations depending on what the fit actually saw.

The output width depends on the fitted category set, not on the number of categories occurring in a particular validation batch. Keep columns aligned to the stored training mapping even if a batch contains only north. An unseen east fixture tests the explicit policy without silently extending categories_ during transformation. For the missing fixture, first ask whether missing was represented in the fit data. If yes, its learned indicator follows that mapping; if not, it follows the unknown-category rule. These checks distinguish stable column identity from changing observed batch contents. The metadata dictionary records that identity so the representation remains interpretable to downstream callers.
tb5 An all-zero unknown indicator does not mean the encoder learned an ‘east’ category. Also, missing and unseen are not universally identical: the fit data and explicit unknown policy determine their treatment.
mle.preprocessing_pipeline
tb1 Your order dataset needs one operation for numerical columns and another for zones before the estimator receives inputs. A fitted pipeline keeps those declared transformations attached to the prediction path instead of asking each caller to recreate them.
tb2 Construct Pipeline([(name, transformer), ..., (name, estimator)]) to chain transformations with a final estimator. Pipeline.fit fits the transformations and final estimator on training data, while predict applies the fitted transformations before prediction. ColumnTransformer applies declared transformers to selected columns, so categorical and numerical columns can use different operations within the same fitted workflow.
tb3 Reuse that fitted pipeline for validation and bounded inference rather than fitting a new preprocessing state. Write assert predicate checks for the declared valid, boundary and failure cases; a false predicate raises AssertionError during ordinary non-optimized execution.
tb4 Imagine distance uses the declared numerical transformer while zone uses the fitted category encoder. ColumnTransformer assigns those operations to their named columns. Pipeline chains the resulting transformation with the final estimator. Fit that workflow on training data, then predict validation through the same fitted object. A fixture should check the expected transformed representation and final output for a valid input, and the supplied boundary and failure cases. If an engineer manually prepares validation with a new encoder, it no longer follows this workflow even if the estimator object is unchanged. Trace one row from selected columns through transformations to the estimator so the distinction between fitting the workflow and applying it is visible.

Trace a complete prediction call rather than testing transformations and estimation as unrelated pieces. The incoming raw columns are selected, their fitted operations are applied and the resulting representation reaches the final estimator. Intermediate pipeline steps must support fitting and transformation; the final step is the estimator. A manually prepared validation array can accidentally skip a step or use a newly learned category order, which is why the fixture should exercise the fitted workflow's own prediction path. Preserve column assignment and fitted state together. Successful estimation of an already transformed array is not evidence that the raw-input pipeline handles the declared contract correctly.
tb5 A pipeline is not a reason to refit for every cohort. Its predict path applies fitted transformations; changing preprocessing state changes the representation presented to the final estimator.
