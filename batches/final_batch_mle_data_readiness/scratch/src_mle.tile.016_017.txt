mle.prediction_boundary_leakage
tb1 A validation result looks unusually strong, but an order's eventual arrival has reached the features. The question is not just whether the evaluation rows were held out. Audit what information reached fitting and what was available for each prediction.
tb2 Leakage uses information not available at prediction time when building a model and can make held-out performance estimates overly optimistic. Audit which rows and fields reach fit operations and each prediction, then remove held-out or future information from those operations. Separate training and evaluation before fitting preprocessing, and call transform rather than fit or fit_transform on held-out inputs.
tb3 Write assert predicate checks for the declared valid, boundary and failure cases; a false predicate raises AssertionError during ordinary non-optimized execution.
tb4 For predictions made at acceptance, a field populated only after arrival is unavailable at the required boundary. Remove it from the prediction input rather than describing the strong held-out result as reliable evidence for this task. Also trace the preprocessing fit: if it saw both training and validation rows, separating the estimator's fit alone did not keep held-out information out of the fitted system. Split before fitting preprocessing and apply transform to held-out inputs. In the bounded fixture, retain explicit checks that no future field enters the prediction and that the fit receives only the designated training rows. The audit is about information flow, not merely whether files have different names.

Distinguish the prediction-time audit from the held-out-fit audit. The former asks whether each input field could have been known at the declared decision time. The latter asks whether any fitted choice used held-out observations. Removing the eventual-arrival feature addresses the first issue but does not repair a scaler already fitted on validation; splitting before fit addresses the second but does not make a future field available at acceptance. Test both information paths in the bounded fixture. The corrected workflow should produce held-out predictions from training-fitted state and decision-available inputs, not merely show a lower score after deleting a suspicious column.
tb5 A held-out label file does not guarantee leakage-free evaluation. Future fields and held-out rows reaching preprocessing fits can both violate the intended boundary.
mle.leakage_safe_features
tb1 You are constructing a feature from an order's earlier records. Some records were added after the prediction was made, and a lookup table has changed since then. Build the feature from the recorded availability boundary rather than today's complete view.
tb2 A feature for a prediction must be derived only from information available when that prediction is made. A list comprehension of the form [row for row in records if row["available_at"] <= prediction_time] selects the records available at the declared boundary. A changing lookup table can yield different training and serving values, so use values from the relevant recorded boundary rather than assuming the latest table is historical.
tb3 Test the feature on the original records and on records augmented with later unavailable observations, asserting that the earlier feature is unchanged. Apply the declared arithmetic feature to the time-filtered records only; for a sum, initialize total = 0 and accumulate total += record["value"] over the accepted list.
tb4 Suppose an order has available records with values 2 and 3 at the decision time, plus a later record with value 7. For the declared sum feature, filter by available_at first, initialize the total to zero, and accumulate only the accepted values. The earlier feature is 5, not 12. Add the later record to the test input and assert that the earlier feature remains 5. If the feature also uses a changing lookup value, retrieve the value appropriate to the recorded boundary instead of treating the current lookup as historical. This test checks the feature computation's response to later information; it does not require later records to be deleted from the source system.

Preserve the calculation's order in the code and the test: inspect availability, decide membership, then update the accumulator. Summing every record and later removing a timestamp field would not remove the later record's contribution. Adding the value 7 is a useful invariance test because the earlier prediction boundary has not changed. The historical lookup check is the corresponding question for changing reference state. Both mechanisms enforce the same declared availability boundary, but they concern different inputs to the feature. Retain a boundary fixture for a record at the exact permitted time under the supplied predicate instead of assuming whether equality is included.
tb5 A timestamp in the source is not enough if the calculation ignores it. The availability filter must precede the arithmetic, and a latest lookup value is not automatically the value available at an earlier prediction.
