mle.dataset_schema_validation
tb1 Your declared dataset has distance and zone fields, with permitted types and value ranges. A table can load successfully while missing zone or containing a distance outside its contract. Schema validation turns those expectations into explicit acceptance checks.
tb2 A dataset schema declares expected features and their permitted representations or values; absent, unexpected or invalid features are schema violations. Compare table.columns and table.dtypes with the declared column/type contract before checking each constrained column. Implement value constraints as boolean predicates and raise an explicit validation exception when a required column, type or value boundary fails.
tb3 Write assert predicate checks for the declared valid, boundary and failure cases; a false predicate raises AssertionError during ordinary non-optimized execution.
tb4 For this invented contract, distance must be numeric and between 0 and 100 inclusive; zone must use the declared representation. A row at distance 0 exercises the lower boundary, while −1 is a failure fixture. A table with an unexpected third feature fails the stated column contract even if all its values look plausible. Compare the column set and types first, then evaluate each constrained column with boolean predicates. Use an explicit validation exception when a required condition fails. Keep fixtures for a valid table, a permitted boundary and a failed condition, so a later change does not quietly alter what the contract accepts. The checks concern the declared schema, not guesses about what a downstream model might tolerate.

Separate a column-contract failure from a value-contract failure. A missing zone field prevents the declared table schema from being satisfied; a present zone field with an invalid representation is a different reason to reject. The numerical limit test also needs its stated inclusive boundary rather than an assumed strict inequality. Write the failure so the caller can identify the violated condition without guessing from a later estimator exception. Replaying both valid and rejected fixtures verifies that the validator is neither accepting everything nor rejecting everything. Its purpose is to enforce the supplied contract before downstream work depends on that contract.
tb5 Loading a table does not validate it. Assertions exercise the fixtures in ordinary non-optimized execution; explicit exceptions enforce rejection of invalid input in the declared validation path.
mle.dataset_cleaning_policy
tb1 An order appears twice, and another has an invalid distance. Cleaning should follow the supplied retain, repair or reject policy, not an engineer's unrecorded preference. The important result includes what happened to the affected observations.
tb2 Use a set of accepted observation keys to test whether a key has already been seen before adding the next accepted key. Use a policy dictionary to choose the declared retain, repair or reject action for each detected invalid or repeated observation. Inspect and clean example data as needed, making representations consistent with its intended training use.
tb3 Implement the declared action with conditional branches and report the affected observation IDs, instead of silently altering the dataset. Write assert predicate checks for the declared valid, boundary and failure cases; a false predicate raises AssertionError during ordinary non-optimized execution.
tb4 Suppose the approved policy retains the first accepted order key, rejects a repeated accepted key, and repairs a specified zone spelling. Start with an empty accepted-key set. After accepting order A, add A; when A appears again, detect the repeat before accepting it. Apply the policy dictionary's action through explicit branches and record A as affected. For order B with the approved spelling issue, record the repair and its ID. A different defect may require rejection rather than that same repair. Test a valid observation, the declared boundary and a repeated-key fixture. This example does not choose a universal deduplication rule: it implements the rule supplied for this dataset and its intended training use.

A useful cleaning report lets a reviewer trace each affected ID back to the applied policy action. Do not combine ‘repaired’ and ‘rejected’ into an undifferentiated issue count: a repaired record contributes different resulting data from a rejected record. Membership in the accepted-key set is also about the accepted observation history, so follow the supplied action order rather than adding every seen key indiscriminately. The repaired fixture should have its expected resulting values checked, while the duplicate fixture should verify that the prohibited repeat was not accepted. Retain valid observations according to the same policy; defect handling should not replace the dataset's stated purpose.
tb5 Cleaning is not permission to silently rewrite observations. A duplicate or invalid record needs its declared action and affected ID reported; the policy decides the action, not merely the presence of a defect.
