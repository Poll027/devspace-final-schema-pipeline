# 03 screens — GENERATOR
Write `batches/<batch_id>/screens.json` (`kind: screens_part`, schema `screens_part.schema.json`) for the assigned tiles. Read `tile_plans.json`, `inputs/path_glossary_bundle.json`, `scenario_asset_registry.json`, playbook §2 and §5.

1. **The plan is law.** Same `step_id`s, types and order; for each planned step copy `concept_ids`, and set `lineage.teaching_block_ids` and `fact_ids` equal to the plan's. `check`/`hands_on` steps carry framing only (title, eyebrow, lede, reward, lineage) — their interactions are stage 04. Extra `remediation` steps (`<tile>.rNN`) are allowed and expected.
2. **Re-voice, don't re-teach.** Turn the glossary teaching blocks into short screen text using the registry's scenario values. Keep every fact's meaning; never add a claim, upgrade a hedge ("commonly" → "always"), close an open list, or add a cause. No concept from `blocked_future_concepts`. **The text must teach on its own** — never "as the video shows".
3. Each `prose` block: one idea, about 90 words or fewer, with `lineage {concept_ids, teaching_block_ids, fact_ids}` using qualified ids (`<concept_id>#f1`, `<concept_id>#tb2`, `<concept_id>#assessment:<capability>`, `#practice`, `#visual`). Stay within the step's `word_budget`.
4. **Visuals:** realise the planned block type (or an allowed alternate in `registry/anchor_mapping.json`) and tag it `lineage.anchors: ["<concept_id>#visual"]`. Data visuals reference registry assets with `asset_ref` — never inline rows. Code/formula/chart outputs are computed in stage 05; do not type them. In a `spreadsheet_grid` the formulas are recalculated in the pinned HyperFormula engine, where a bare `TRUE`/`FALSE` inside a formula yields `#NAME?`: write `TRUE()`/`FALSE()` (e.g. `=VLOOKUP(D2,A2:B3,2,FALSE())`); if the lesson text uses Excel's `FALSE`, add one sentence saying this embedded engine needs `FALSE()` for the same exact-match behaviour.
4b. **Query results (SQL paths):** when a table is the OUTPUT of a query (DISTINCT, WHERE, GROUP BY, JOIN ...), give the `data_table` a `result_of` `{runtime: "sql", sql, asset_mounts: [{asset_id, mount_path: <table name>}]}` instead of an `asset_ref`. Never use `asset_ref` + `max_rows` or typed rows to imitate a result: the player would show the wrong rows. `assemble_tiles.py` runs the query and stores `result`; never write `result` yourself. A before/after pair shows the same query before and after the change, both as `result_of` when the change is a query change.
5. **Video steps:** a `media_group` with `segment_ids` only (assemble copies segments, summaries and bridge notes from the glossary).
6. **Recap:** the planned takeaways plus an `up_next` block naming the next tile's first idea.
7. Add a short `remediation` step for the first check/hands-on of each concept (same dataset, one clear contrast). It must re-teach the facts the check measures (`measures[].fact_ids`): if a concept has checks that measure different facts (e.g. one tests rows/columns, another tests well-formed tables), give each its own remediation step, because the learner who fails a check is sent to that step.
8. Gate: `schema_check.py screens_part.schema.json batches/<id>/screens.json`; then, once interactions exist, `assemble_tiles.py` + `validate_tile.py`.

Mistakes to avoid: unqualified fact ids; text blocks with no lineage; any mention of the video; examples that disagree with registry values (ids, cities, numbers); step text over budget; paraphrase that changes meaning; showing a column the dataset lacks; forgetting `#visual` on the visual block.
Reply with: artifact path, step counts, anything you were unsure about.

**Images exist only if stage 01 rendered them:** look for `asset_kind: image` assets in `scenario_asset_registry.json`. When the plan's visual is a plot or a before/after of plots and a registered image shows it, use `annotated_image` (`asset_id`, `alt_text` copied from the asset, optional `hotspots`): a before/after is two consecutive `annotated_image` blocks, each introduced by a one-line `prose` block saying which is which; this is accepted as the alternate of `before_after`, and `chart` visuals accept it too. Never present a chart's look as `code_walkthrough` panels when a registered image shows it. You cannot render images in this stage: if no image asset exists for what a step needs, fall back as below. Without a registered image, `annotated_image` is not available (a plan that says `annotated_image` accepts the alternate `diagram`: draw the screen, grid or UI state as an SVG diagram with labelled callouts, or a `spreadsheet_grid` when the point is cell addresses/formulas). `spreadsheet_grid` formulas are run in the engine: give `cells[].formula`, never type `computed_values` (assemble derives them).

**Inspect-and-judge `hands_on` steps.** When a `hands_on` step's `planned_interaction_type` is `classify` or `choice` (the concept is read-and-judge because the player cannot run PyTorch, GPU, Docker, cloud, uvicorn, a shell or a socket), its title and lede are framing for a judgement task: title like "Review ..." / "Judge ...", lede asking the learner to read the supplied excerpt(s) in this step and decide which are correct, defective or unsafe. Never write "Implement", "Build", "Run", "Execute", "Provision", "Train", "Commit" or "Submit" for such a step; never name a workspace (`ws.*`), README or registered files; never ask for evidence from the learner's own execution; never add disclaimers that the classification cannot verify or complete the practice.

**Source code is always shown as code:** any Dart, YAML, XML, PHP or Vue longer than a single identifier or short expression goes in a `code_walkthrough` block (`language` "dart", "yaml", "xml", "php", "vue", ...), never inline in prose or in table cells.
