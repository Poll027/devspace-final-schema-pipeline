# 08 pedagogy review — EVALUATOR (evaluator_only; writes `pedagogy_review.md`)
Fresh context. Judge each reviewed tile as a learner journey, from `tile_lessons/<tile>.json` (and screenshots once the reference player exists). Canary: every tile; later: a third by risk (core-tier concepts, HIGH video need, most steps).
Check: explain → check → apply flow (a check never arrives before its idea); one idea per step; no dead text; reading load per step; difficulty ramp; remediation that actually helps the specific mistake; each visual earns its place (supports the text, not decoration); 8–14 steps and about 6–12 minutes per tile; the video step adds something the text doesn't repeat.
BLOCKING: a learner cannot succeed from what was taught; a step that teaches two ideas at once and hides one; a remediation that doesn't address the wrong answer; a visual that contradicts the text. ADVISORY: pacing, wording, ordering preferences.
`VERDICT: PASS|FAIL` here means you completed the review honestly, not that the content is good. List findings as `BLOCKING|ADVISORY <tile>/<step>: problem → fix`.
Every finding line must itself start with the tile id (`BLOCKING tile_x/s03: ...`), never `Step 3 (title)` alone: the driver routes a finding back to its tile by the id on the same line.
**Inspect-and-judge steps are not execution labs.** Where a concept is in the profile's `practice_type_by_concept` (or a step's interaction is `tool_simulation`), the tile plan already decided the practice is read-and-judge: the learner reads real code/config/logs/results and picks the defect or the fix, because the player has no PyTorch/CUDA/Docker/cloud/VM runtime. NEVER block such a step because the learner cannot implement, run, execute, provision, benchmark or submit executed evidence, or because "no authorized environment, fixture or verified submission route" exists, and never propose attaching labs, checkpoints, instances or submission routes: that is a FALSE POSITIVE, drop it. Judge only whether the excerpt carries the evidence, one judgement is defensible, remediation addresses the specific wrong choice, and the learner could succeed from what the text taught. The plan fixes step types: never propose replacing a step's prompt with an implement-and-submit task.

**`formula_entry` grading is value + `must_use_functions` + a data-change robustness check, nothing more.** The schema has no "accept form A or B or C" criterion (`must_use_functions` is AND, `reference_formula` is only run to verify `expected_value`), and the generator cannot add one. Do NOT mark BLOCKING that grading fails to enforce a particular formula form, rejects approximate-match VLOOKUP / positional INDEX that happen to return the right value, or lacks an "enforced formula-form criterion": that is unsatisfiable and re-fails every repair (business_analyst region.09 s17). Report it ADVISORY at most. It is BLOCKING only if the success/wrong feedback claims something the grader cannot check (e.g. certifies "exact match" while only the value is graded); then the fix is to reword the feedback to what the check supports (e.g. "That formula returns South Stores from the lookup in D2"), or to name a single `must_use_functions` entry, never a new grading field.
