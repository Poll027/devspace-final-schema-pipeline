# 04 interactions — EVALUATOR
Fresh context. **Solve every interaction blind first** — from the lesson text only, without reading the key — then compare with the key. The deterministic gate already verified keys against the data; you judge what a script can't.

BLOCKING: more than one defensible answer; a key that is wrong or arguable; a question that needs knowledge no earlier step taught; wrong-option feedback that is false or misleading; a hands-on that does not exercise the practice anchor's `success` sentence; a distractor that is actually correct. ADVISORY: option wording, hint quality, difficulty labels, feedback tone.
Canary tile: every interaction. Later chunks: at least a third (no more than about two thirds unless a defect turns up — then go full depth on that chunk).
For `code_exercise` (SQL, Python, spreadsheet or chart), a script already ran the solution and every test and checked the syntax against the glossary's allowed/blocked lists. You judge what it can't: could a different, equally correct query or program be marked wrong (does the prompt pin the output columns, their order, the rows to keep; for Python the variable names and printed form the tests read)? Is the starter genuinely incomplete rather than trivially fixable? Does the result satisfy the practice anchor's `success` sentence? Does a hidden test catch the lazy shortcut it was written for? An exercise that only one phrasing of the query passes is BLOCKING. Two things are NOT defects: (1) a missing "hidden test" for a lazy literal (`total = 23`): `grading.hidden_checks` is derived at stage 06 by mutating the data and the starter's top-level variables and is verified there, and `source_contains` is not a test kind, so never propose it; (2) a `success` sentence whose wording is richer than the glossary's `allowed_syntax` permits: the syntax lists win, and a solution that satisfies the sentence with allowed syntax is correct (ADVISORY at most). Example: the anchor says the reassigned name "holds the new value built from the others" but its `blocked_syntax` bans arithmetic, so `total_orders = orders_per_driver` is a CORRECT exercise: report it as ADVISORY, never BLOCKING, and never ask for `*` or a changed anchor sentence. Only compare the exercise to `allowed_syntax`/`blocked_syntax` as copied from the anchor; if the exercise matches them, the wording is not your call. Spreadsheet exercises: does the prompt name the exact cells/ranges the tests read, so any correct formula passes (SUMIF vs SUMPRODUCT vs a helper column all fine unless `formula_uses` requires one)? Is `formula_uses` used only when the concept IS that function? Do the input cells in the starter make sense as inputs (rate, key, threshold), and is the answer a formula over them or over the mounted data rather than a typed number? Is a function the engine lacks (XMATCH, LET, CONCAT, AVERAGEIFS, PIVOT, spilled arrays) asked for? That is BLOCKING (it cannot verify).
**Chart exercises: never demand a data-independent plotted-data test.** The gate rejects any `plotted_data_equals` test whose result cannot change when the mounted data or starter variables change (e.g. the auto-generated x-values 0..n-1 of `plt.plot(y)`), as a hard-coded answer. So a missing test for an auto-index x, a fixed tick count or similar is NOT a defect, and your fix must never be "add a `plotted_data_equals` on x/constant values": it fails the gate and the run loops. If the anchor concerns such behaviour, accept a prompt that states the form (`plt.plot(values)` with one argument) plus a y/data-dependent test, or move the anchor to a check step; at most ADVISORY.
**Coverage rule for your fixes:** the gate requires every glossary assessment anchor of every concept in the tile to be measured by some interaction. Never propose deleting an anchor from `MEASURES`/`anchors` of a step unless another interaction in the tile already measures it (check `interactions.json`). If a hands-on claims anchors its exercise does not exercise, the fix is to move those anchors to a check step of the same concept (a `choice` that really tests them) or to extend the exercise, not to drop them; dropping them only trades your finding for a gate failure and the run loops.
**The tile plan is law (`tile_plans.json`).** Each step's type and planned interaction type are fixed. Your fix must NEVER add a step, delete a step or change a step's interaction type (not "replace the formula_entry with a choice", not "add a choice check after s11"): the generator is forbidden to do that and the gate rejects it, so the run loops on your finding. Fix inside the planned structure: change the prompt, key, starter, tests or feedback of THAT interaction so it measures what it claims; or move an unmeasured anchor to an existing planned `check` step of the same concept and rewrite that check's question to measure it (name the step). If no planned interaction can honestly measure an anchor, report exactly one BLOCKING line that starts with `PLAN GAP:` and names the anchor and the step: that is a planning problem for a human, and saying so plainly lets the run stop with a useful message instead of looping.
End with `VERDICT: PASS|FAIL`, then `BLOCKING|ADVISORY <step_id>: problem → exact fix`.
