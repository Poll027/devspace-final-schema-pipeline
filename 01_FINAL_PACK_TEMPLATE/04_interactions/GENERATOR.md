# 04 interactions — GENERATOR
Write `batches/<batch_id>/interactions.json` (`kind: interactions_part`, schema `interactions_part.schema.json`): exactly one interaction per `check`/`hands_on` step in the plan. Read `tile_plans.json`, `screens.json`, `inputs/path_glossary_bundle.json`, `scenario_asset_registry.json`.

1. Use the **planned interaction type**. `measures` lists `{concept_id, capability, fact_ids}` for the planned anchors (capabilities must be glossary assessment anchors). A `hands_on` includes `anchors: ["<concept_id>#practice"]` and must make the practice anchor's `success` sentence true.
2. **Test only what earlier steps taught by text.** Never test a fact first met in the video or later.
3. **Answer keys are predicates against registry assets**: rows by `where`+`occurrence`; cell answers carry `expect_value`; `classify` items carry `source` and the grading carries `role_map`; `find_issues` keys come from the variant's `planted_issues` (same ids and locations). Never hand-type a value the data can supply.
4. **One defensible answer.** If a thoughtful learner could argue for a second option, rewrite the question.
5. **Distractors come from real misconceptions** (glossary `misconceptions` first, then common errors for the concept). Every wrong option gets feedback saying *why* it is wrong, grounded in the facts — no new claims.
6. `feedback`: correct and incorrect messages, 1–2 hints that don't give the answer, `remediation_step_id` for the first check/hands-on of each concept.
7. Difficulty ramps intro → core → stretch across the tile. `grading_mode: client` for checks; `server` only for assessment tiles. `standalone: true` only if the prompt needs no earlier screen.
8. Gate: `assemble_tiles.py` then `validate_tile.py` until 0 errors (they check keys against the data and the taught-before-tested rule).

9. **`code_exercise` (SQL).** Only where the plan says `code_exercise` and the runtime is `sql`. A script runs your solution in the pinned DuckDB-WASM (`registry/runtimes.json`) and checks everything below, so write it to pass that check:
   - `public.runtime = {kind: "sql", version: <the pinned version in registry/runtimes.json>}`. `workspace.files`: one `editable` starter file (comments plus a partial query is ideal; never the solution) and `entry` naming it. `workspace.asset_mounts`: each registry dataset with `mount_path` = the SQL table name the glossary examples use.
   - `constraints.allowed_syntax` / `blocked_syntax`: copy the glossary practice anchor's `live_code` lists verbatim. The solution may use only allowed syntax; anything else fails the gate. Check your solution against those lists yourself first.
   - `grading.solution_files`: same path as the entry file. `grading.tests`: at least one `query_result_equals` with `spec.expected = {columns, rows}`, the result the solution produces (the gate re-runs the solution and rejects an expected that differs). Set `spec.ordered: true` only if the prompt requires an order. Values in `expected`: numbers for integers, floats and decimals (12.5, not "12.50"); dates as "YYYY-MM-DD"; timestamps as "YYYY-MM-DD HH:MM:SS" (UTC); `true`/`false`; `null`. If the gate says your `expected` differs, its message shows what the solution really returned: fix the solution or the prompt, never edit `expected` to hide a wrong query. Hard-coded answers are caught for you: assemble derives `grading.hidden_checks` by mutating the mounted data (drop a row, duplicate a row, change a cell) and recording the solution's result on each copy, so never write `hidden_checks`. The gate rejects an exercise whose result does not change when the data changes, so the task must ask for something the data determines (never a constant). An optional hidden test with `spec.mount_variants` (`{table: variant_id}`) may add a registry variant too. Add `forbidden_syntax` tests (`spec.descriptors`) only for descriptors the practice blocks.
   - **Several queries in one exercise** (the practice anchor says "write two queries", or its `success` sentence names a first and a second result): put the statements in the one file in the order the prompt gives them, and add one `query_result_equals` test per query with `spec.statement` = that query's 0-based position in the file (`0` is the first statement). Every query the `success` sentence names needs its own test, or the evaluator blocks the untested query. Without `spec.statement` a test grades the last statement that returns rows.
   - The prompt names the exact output columns (and their order) and the filter/sort the learner must apply, so any correct query returns the same rows. A prompt that a correct query could answer with different columns or rows is a defect.
   - The starter must NOT pass the tests. Never write `execution_provenance`; assemble computes it from a real run.
   - The `success` sentence of the practice anchor must be true of the solution's result.
9b. **`code_exercise` (Python / pandas).** Only where the plan says `code_exercise` and the runtime is `python`. A script runs your solution in the pinned Pyodide (`registry/runtimes.json`; Python 3.13, pandas and numpy available, scipy on request) and checks everything below:
   - `public.runtime = {kind: "python", version: <the pinned version in registry/runtimes.json>, packages: [only what the exercise imports: "pandas", "numpy", "scipy"]}`. `workspace.files`: one `editable` starter file (the imports, the data load and a comment is ideal; never the solution) and `entry` naming it. `workspace.asset_mounts`: each registry dataset as a CSV file, `mount_path` = the file name the glossary examples read (e.g. `orders.csv`, read with `pd.read_csv('orders.csv')`).
   - `constraints.allowed_syntax` / `blocked_syntax`: copy the practice anchor's `live_code` lists verbatim. The gate reads your solution's parse tree: using anything the lists do not allow (a loop, an f-string, `len()`, a method the concept has not taught) fails it. Write the simplest solution that uses only allowed syntax; check each construct against the allowed list first. The names `pd`, `np`, `plt`, `sns` are not checked, the methods you call on them are.
   - `grading.solution_files`: same path as the entry file. `grading.tests` (kinds): `stdout_equals {expected}` (what the program prints, compared after trimming line ends); `value_equals {expr, expected}` (a Python expression evaluated after the program ran, e.g. `total`); `dataframe_equals {expr, expected: {columns, rows}, ordered?}` (e.g. `big[['customer_id']]`); `function_call {function, args, kwargs?, expected}` (a function the learner defines); `forbidden_syntax {descriptors}` only for descriptors the practice blocks. Values in `expected` are plain JSON: numbers, strings, `true`/`false`, `null` (a missing value), lists; dates as "YYYY-MM-DD". `tolerance` for floats.
   - **Never type `expected` from memory**: run the solution mentally against the data and compute it, then the gate re-runs the real program and rejects a mismatch (its message shows what the solution returned: fix the solution or the prompt, never edit `expected` to hide a wrong program).
   - **A hard-coded answer must fail.** `assemble` derives `grading.hidden_checks` by changing the mounted data (drop/duplicate a row, change a cell) and by changing the numbers/strings of the starter's top-level `name = value` assignments, and recording the solution's result on each copy. The gate rejects a test whose result never changes: the task must ask for something the data or the starter's variables determine. For a pure computation with no data, the starter assigns the inputs (`width = 4`) and the solution must use those names. A `function_call` test needs at least TWO calls of the same function with different arguments.
   - **Type and conversion tests must still vary.** `type(x).__name__` or a printed literal never changes when the starter changes, so it fails the hard-coded-answer gate. The starter assigns the inputs (`raw = "42"`, `price = 3.5`) and the solution converts/uses THOSE names. Grade with an expression that mixes type and value: `value_equals` `expr: "type(result).__name__ + ':' + str(result)"`, expected `"int:42"`. Never print a bare literal (`print(type(3.5))`): `stdout_equals` is only for output computed from starter names.
   - The prompt names the exact variable, column names and output form the checker reads (`result`, `big`, the printed text), so any correct program passes. A prompt a correct program could answer in a form the test would reject is a defect.
   - The starter must NOT pass the tests. Never write `execution_provenance` or `hidden_checks`.
   - The practice anchor's `success` sentence must be true of the solution's result.
   - If the `success` sentence's wording ("built from the others") seems to need more than `allowed_syntax` permits, `allowed_syntax`/`blocked_syntax` win: satisfy the sentence with the construct that is allowed (e.g. a reassignment that copies or reuses another name), never add syntax the concept has not taught, and say in your reply which reading you took.

Mistakes to avoid: key typed instead of derived; two defensible answers; a distractor that is correct under a valid reading; testing an untaught fact; a capability that isn't a glossary anchor; a hands-on that can be completed without meeting the `success` criteria; "the table above" in a `standalone` prompt; a `classify` set with no trap item when the anchor is about a trap (e.g. numeric-looking labels); a SQL or Python `expected` typed from memory instead of from running the solution; a Python solution that uses a loop, f-string, helper or method the concept has not taught; a Python test on a variable the starter never defines; a solution that quietly uses syntax the concept has not taught (e.g. WHERE in a SELECT-only concept); a starter that already returns the answer; a prompt that does not pin the output columns.
