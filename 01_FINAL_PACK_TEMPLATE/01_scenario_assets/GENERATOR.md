# 01 scenario + asset registry — GENERATOR
Write `batches/<batch_id>/scenario_asset_registry.json` (schema `scenario_asset_registry.schema.json`) for the batch scope.

Read `inputs/path_glossary_bundle.json` (all concepts in scope: teaching blocks, anchors) and the playbook §4–5.

1. **Mine the glossary's own example vocabulary first** (tables, columns, people/places, numbers, tools it mentions in teaching blocks and anchors) and list it in `scenarios[].glossary_example_vocab`. The registry must be consistent with what the taught text already says.
2. One scenario per path (or per region if the glossary genuinely uses different domains): a short, concrete, fictional but realistic setting.
3. **Datasets**: the smallest table that supports every concept in scope. Every column/value the glossary examples rely on must exist. Declare `semantic_role` for every column; set `numeric_looking_label: true` for digits used as labels (these are the glossary's misconception traps). Authored rows only — no invented real-world facts.
4. **Variants** (messy/edge versions) only through declared ops (`set_cell`, `duplicate_row`, `drop_rows`, `drop_columns`). Record `planted_issues` with predicate `locations` (`where` + `occurrence` + `column`) and a `rule` where the kind needs one (impossible_value, inconsistent_category, ...).
4b. **Every planned `find_issues` needs a defective variant.** Stage 02 maps a concept's practice anchor of type `field_selection` or `data_cleanup` to a `find_issues` interaction whenever its objective/success text mentions flag, problem, issue, quality, duplicate or missing (`registry/anchor_mapping.json` `interaction_keyword_rules`), and stage 04 can only grade it against a registered dataset VARIANT whose `planted_issues` is non-empty (a dataset holding only correct records yields `grading/issues: []` and `goal_count: 0`, which no repair can fix). So for each such concept register, on the dataset its anchor reads, at least one variant built with declared ops that plants the defect the practice text describes (a missing tag, a duplicate, an owner left blank, ...), with `planted_issues` entries that hold after the ops. Do this for every concept in scope with such an anchor, not only the first.
5. Other asset kinds (`code_workspace`) only if an anchor needs them.
5b. **Images (rendered plots).** If a concept's glossary `visual_anchor` or teaching text depends on SEEING a plot (how a chart looks, a style or palette change, the effect of an axis limit or a bin count, labelled vs unlabelled, a comparison of chart types), render each picture and register it as an `image` asset; stage 03 can only use pictures registered HERE, so render every picture the batch's concepts need. Write `working/plots.json` (format in the docstring of `render_plot.py`: `asset_id` like `img.<what>`, `scenario_id`, `title`, `alt_text` describing what the picture shows, `datasets` to mount, `code` that reads the mounted CSV and draws ONE figure) and run `python3 00_FINAL_PIPELINE_CORE/scripts/render_plot.py batches/<batch_id> working/plots.json --registry`: it renders in the pinned engine, writes `assets/<id>.svg` plus a provenance sidecar, and adds the `image` assets to the registry (run it AFTER you have written the registry, then run the gate). A before/after pair is TWO assets (e.g. `img.bars_default`, `img.bars_ggplot`) drawn from the same data and the same code except the one thing being taught. Matplotlib/seaborn only, over datasets already in the registry. Never type or edit an SVG: the gate re-renders every image from its sidecar code and rejects any difference.
5c. **Inspect-and-judge concepts (read `00_FINAL_PIPELINE_CORE/registry/path_profiles/<path_id>.json`).** Concepts listed in `practice_type_by_concept` are NOT run by the learner: their glossary practice anchor describes live code, a GPU, Docker, a shell, Redis, a cloud service, a CLI or similar, but the player has no such runtime, so the learner instead READS real code, config, logs or metrics and judges them (a `classify` or `choice` interaction whose items carry the excerpt as plain text). For those concepts create NO `code_workspace`, NO executable runtime, host binding, credentials, instance, GPU or cloud resource: nothing is provisioned, and the interaction text itself carries every excerpt. BUT still register small READ-ONLY `dataset` assets wherever the glossary `visual_anchor` is a `data_table` or `spreadsheet` (or the teaching text compares figures in a table): the rows the anchor describes (metrics, run logs, comparison or eligibility rows), with declared columns and semantic roles, consistent with the taught text. The screens stage can only show a `data_table` block from a dataset asset, and the plan makes that table mandatory, so without it the region can never pass. The dataset is shown, never executed. A region with no other asset still needs at least one dataset. Keep the scenario vocabulary consistent (names, services, numbers) so later steps can quote it. Do not add assets for them just to satisfy the practice anchor's scaffolding sentences.
6. Gate before handing off: `python3 00_FINAL_PIPELINE_CORE/scripts/validate_tile.py batches/<batch_id> --registry` must PASS.

7b. **Python / pandas exercises:** a dataset is mounted as a CSV (header row, then the rows, empty cell = missing). Use the file/column names the glossary's Python examples use; give enough rows and variants for hidden checks, and make sure the rows contain what the practice is about (missing values, duplicates, mixed types) so a hard-coded answer cannot pass.
7. **SQL paths:** each dataset becomes a SQL table the learner queries. Use the table and column names the glossary's SQL examples use, declare real column `type`s (`integer`, `number`, `string`, `date`, `boolean`) because the SQL engine loads them as such, and give enough rows (and variants) for hidden tests to distinguish a correct query from a lazy one.

Mistakes to avoid: row width != column count; semantic_role contradicting type; a planted issue that does not hold after the ops; wrong `occurrence` for duplicates; a dataset too small/narrow for later tiles; values that contradict glossary examples (a city or column the text names but the table lacks); two defensible readings of a column's role.
